the first thing your agents need is a control plane

no matter what coding agent you use, it gets more useful when authority, proof, and the human return path are explicit.

the first useful thing to build around a coding agent is a control plane: a place where the agent can tell what it is allowed to do, what it must prove, and when it needs to come back to you.

this is the lesson from building admin.anipotts.com. the product starts as a read-only operator dashboard, then a content review surface, then a guarded write path. the live controls come after the state model is boring and obvious.

the spine is simple: intent -> authority -> operation -> proof -> state.

safe lanes versus hard gates

an agent should not have to ask permission for every small move. if the lane is safe, it can inspect, edit, verify, commit, push, and open a draft PR.

other work needs a hard gate. dns, auth, secrets, env, production content stores, outbound sends, live endpoints, payments, and destructive cleanup all need explicit authority. the point of the control plane is to make that split visible before the agent touches the thing.

intent authority operation proof state

proof beats trust

a finished agent task should leave proof another agent can inspect. the proof can be a commit, a PR, a command result, a deploy record, a screenshot, or a blocked-action list. the important part is that it survives the chat.

chat memory is too soft for real work. once multiple agents are touching the same repo, the durable object matters more than the explanation. if the next agent cannot pick up from the artifact, the system is still missing the control plane.

NEEDS-ANI is the human syscall queue

the human return path should be small. NEEDS-ANI has one job: ask for the decisions only Ani can make.

that means approval, choice, account-side action, identity, payment, secret setup, final taste, or a source-delete call. routine status belongs in commits, PRs, handoffs, and proof records.

admin is the control plane

admin.anipotts.com should make state legible before it makes state mutable. content, fleet state, handoffs, approvals, and proof belong in one surface because agents need to know what they are allowed to do next.

the order matters. read-only first. preview second. guarded writes after the authority model is real. the system gets safer when the live button is the last thing added.

working close

the future looks like a system where agents know what they can do next, what proof they owe, and when the right move is to return one clear decision to Ani.
